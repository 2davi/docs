# Phase 8 프롬프트 — 관측성 & 아키텍트 종합 (Observability & Architect Capstone)

> **사용법**: 공통 프롬프트(`00-common-prompt`)를 먼저 붙여넣고, 이어서 이 파일을 붙여넣는다.

## 이 채팅의 Phase
**Phase 8 — 관측성 & 아키텍트 종합.** 시리즈의 마지막. 클러스터를 *들여다보는 눈*을 붙이고, 8개 Phase를 아키텍트 관점으로 엮은 뒤 시험을 모의한다. 15.8GiB 제약상 관측 스택은 **필요할 때 띄우고 끝나면 내린다**.

## 선행 학습 상태
- **Phase 1~7** ✅ — 전 도메인을 세우고·통제하고·부숴봤다. 이제 관측으로 닫는다.
- 이번이 **Phase 8 (시리즈 마지막)**.
- *(Phase 7 인계 메모 붙여넣기)*

## 허브와의 연결점
관측성은 조정 루프를 *외부에서 계측*하는 일이다 — 원하는 상태로 수렴하고 있는지, 어디서 지연·드롭·오류가 나는지를 메트릭·로그·트레이스로 읽는다. 트러블슈팅(Phase 7)이 사후 진단이라면, 관측성은 상시 가시성.

## 이 Phase의 하위 토픽 (왜 → 정의 → 사용 → 한계)
1. **왜**: 침묵하는 시스템은 디버깅 불가. 관측 3축(메트릭·로그·트레이스)의 역할 분담을 알아야 옳은 도구를 고른다.
2. **메트릭**: Prometheus 수집·PromQL 기초, kube-prometheus-stack(필요 시만 상주), 핵심 클러스터 메트릭.
3. **시각화**: Grafana 대시보드, 골든 시그널(지연·트래픽·오류·포화).
4. **흐름 관측**: Hubble로 L3/L4/L7 흐름·드롭·정책 위반 실시간 관찰(Phase 4의 회수).
5. **로그·트레이스 개념**: 중앙 로깅·분산 트레이싱이 "왜 이 요청이 느렸나"를 端-to-端으로 답하는 원리.
6. **아키텍트 회고**: 8개 Phase를 조정 루프·계층·트레이드오프 관점으로 재구성. 네가 내린 설계 결정(린 스택·VirtualBox 상한·kube-proxy 대체)의 근거를 말로 방어.
7. **시험 마무리**: killer.sh 세션 2회(등록에 포함, 실제보다 어려움), CKA/CKAD 도메인 자기평가, 약점 도메인 집중 드릴, `kubectl` 명령형·별칭·vim 속도. (출처: [Linux Foundation CKAD](https://training.linuxfoundation.org/certification/certified-kubernetes-application-developer-ckad/))
8. **한계**: 관측 스택 자체의 리소스 비용(15.8GiB에서 상시 상주 불가), 계측 과다의 노이즈, 트레이싱 도입의 계측 부담.

## CKA/CKAD 매핑 + 완료 정의(DoD)
- **CKA/CKAD**: Observability and Maintenance + 전 도메인 종합.
- **DoD**: ①관측 스택을 1회 구성해 핵심 메트릭·대시보드·Hubble 흐름 확인, ②8개 Phase를 아키텍트 관점 한 장으로 회고(설계 결정 방어), ③killer.sh 2회 완료 + 약점 도메인 식별·보강, ④CKA/CKAD 도메인 자기평가 통과선 도달.

## 시작 지시
**진단 질문 1개**부터(예: "메트릭·로그·트레이스 셋 중, '왜 *이 한 요청*이 느렸나'를 서비스 경계를 넘어 端-to-端으로 답하는 건 어느 것이며 왜인가? 나머지 둘은 이 질문에 왜 부족한가?"). 채점 후 1번부터.

## 마감
이 Phase가 끝나면 공통 프롬프트 §7 **"Phase 마감 점검 의식"**을 실행하고, **시리즈 전체 회고**를 추가한다(8개 Phase DoD 총점검 + CKA/CKAD 응시 준비도 판정). 시리즈 종료.
