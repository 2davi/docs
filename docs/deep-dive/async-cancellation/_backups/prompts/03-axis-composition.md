# 축3 프롬프트 — 합성·동시성 (Composition & Concurrency)

> **사용법**: 공통 프롬프트(`00-common-prompt`)를 먼저 붙여넣고, 이어서 이 파일을 붙여넣는다.

## 이 채팅의 축
**축3 — 합성·동시성.** 단일 작업 취소 다음 단계: 여러 작업을 묶고, 병렬을 제어하고, 취소를 형제 작업에 전파하는 오케스트레이션.

## 선행 학습 상태 (이전에 정복한 축)
- **코어(AbortController)** ✅ — 특히 `AbortSignal.any()`(OR 합성)과 사유별 컨트롤러 구성.
- **축1 (수명·정리)** ✅ — ERM/`using`, `WeakRef`.
- **축2 (EventTarget 기반)** ✅ — `EventTarget` 상속, `CustomEvent`/`dispatchEvent`, 리스너 옵션, 전파.
- 이번이 **축3**. 이후: 축4 → 축5.
- *(직전 축[축2]의 인계 메모를 여기 붙여넣기)*

## 코어와의 연결점
코어의 `AbortSignal.any([])`가 "여러 취소 사유 합성"의 씨앗이었다. 축3은 그걸 *작업 합성*으로 확장한다 — Promise 결합자와 시그널이 만나는 지점, 한 작업의 실패가 형제를 취소하는 패턴.

## 이 축의 하위 토픽 (왜 → 정의 → 사용 → 한계)
1. **왜**: 실무는 단일 fetch가 아니라 여러 비동기의 조율. 부분 실패·병렬 폭주·중복 요청이 새 문제.
2. **Promise 결합자 정밀**: `all`(하나 reject 시 전체 reject — 나머지는?), `allSettled`, `race`, `any`(`AggregateError`). 각각의 정확한 settle 의미.
3. **결합자 × 취소**: `race`로 만든 타임아웃 vs `AbortSignal.timeout` 비교, 한 작업 실패 시 형제 취소(공유 컨트롤러로 전파).
4. **동시성 제한**: 세마포어/큐/풀 패턴. (내장 없음 — 직접 구현 골격.) `Promise.all`을 무한정 풀면 왜 위험한가.
5. **cancel-previous / stale-response 정식화**: 검색창 패턴, 버전 토큰 vs `AbortController`의 트레이드오프.
6. **한계**: 결합자의 부분 실패 시 *취소되지 않은 형제*의 자원 누수, 동시성과 순서 보장의 충돌.

## 시작 지시
**진단 질문 1개**(예: "`Promise.all`에서 하나가 reject되면 나머지 진행 중인 Promise들은 어떻게 되나?")로 시작. 채점 후 1번부터.
