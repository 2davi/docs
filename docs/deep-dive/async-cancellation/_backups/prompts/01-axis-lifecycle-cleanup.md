# 축1 프롬프트 — 수명·정리 (Lifecycle & Cleanup)

> **사용법**: 공통 프롬프트(`00-common-prompt`)를 먼저 붙여넣고, 이어서 이 파일을 붙여넣는다.

## 이 채팅의 축
**축1 — 수명·정리.** 리스너·타이머·연결을 "까먹지 않고" 정리하는 것을 언어 차원에서 강제하는 메커니즘. 코어에서 내내 손으로 하던 정리(`removeEventListener`, `{ once }`, `finally`)의 *언어적 결말*.

## 선행 학습 상태 (이전에 정복한 축)
- **코어(AbortController)** ✅ — 공통 프롬프트 §3 참조. 특히 GC·도달 가능성·옵저버.
- 이번이 **축1 (5축 중 첫 축)**. 이후: 축2(EventTarget) → 축3 → 축4 → 축5.
- *(직전 축 인계 메모가 있으면 여기 붙여넣기 — 축1은 코어 직후라 보통 비어 있음)*

## 코어와의 연결점
코어 GC 논의의 결론은 "장수 시그널에 리스너를 안 떼면 샌다"였다. 축1은 그 "떼는 행위"를 스코프 종료 시 **자동화**한다. 즉 코어가 던진 숙제(수동 정리의 취약성)에 대한 언어 차원 해답.

## 이 축의 하위 토픽 (왜 → 정의 → 사용 → 한계)
1. **왜**: 수동 정리의 취약성 — 리스너/타이머 누락, `try/finally` 보일러플레이트의 한계와 중첩 시 가독성 붕괴.
2. **ERM 개념**: `using` / `await using` 선언. 블록 스코프를 벗어날 때 자동 dispose 호출.
3. **프로토콜**: `Symbol.dispose`(동기), `Symbol.asyncDispose`(비동기). 객체가 이걸 구현하면 `using` 대상이 된다.
4. **`DisposableStack` / `AsyncDisposableStack`**: 여러 자원을 묶어 정리, LIFO 정리 순서.
5. **AbortController와 결합**: 컨트롤러/리스너를 Disposable로 감싸 스코프 종료 시 자동 `abort()`+정리. `{ signal }` 옵션 + `using`의 시너지.
6. **`WeakRef` / `FinalizationRegistry`**: 약한 참조, 수거 후 콜백. 코어 GC 논의의 *언어 도구*. (Node 누수 디버깅에서 본 그 WeakRef.)
7. **한계**: 브라우저/런타임 지원 현황과 트랜스파일/폴리필 필요성, `FinalizationRegistry`의 **비결정성**(콜백 타이밍 보장 없음, 남용 금지), `using` 미지원 환경 대응.

## 시작 지시
코어 GC 스레드에서 자연스럽게 이어, **진단 질문 1개**부터 던져라(예: "리스너 정리를 `finally`로 하면 뭐가 부족한가?"). 답을 채점한 뒤 1번부터 전개.

## 마감
이 축이 끝나면 공통 프롬프트 §6 **"축 마감 점검 의식"**을 실행해 누락을 점검하고 **인계 메모**를 만든다. 다음 축은 **축2(EventTarget 기반)**.
