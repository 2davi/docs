# STEM-CHR-0001: Stemma Project Charter {#stem-chr-0001}

## 요약 {#summary}

Stemma는 `blog.the2davi.dev` 도메인으로 구동할 블로그 엔진의 개발용 코드네임이다. 글을 블록 단위로 편집하고 발행하며, 글의 편집 이력을 Git 커밋 그래프와 같은 구조로 보존한다. 마크다운으로 개발 노트를 쓰는 사람을 실사용자로 겨냥한다. 이 헌장의 범위는 8단계까지이며, 이 중 5단계에서 VitePress로 만든 지금의 정적 블로그 `docs.the2davi.dev`를 이 엔진으로 옮기고 내린다.

## 문서의 역할 {#document-role}

이 프로젝트 헌장은 Stemma를 왜 만들고, 어디까지 만들고, 언제 끝났다고 보는지를 정한다. 목적과 우선순위, 규모, 비용 한도, 범위, 각 단계별 시작 조건과 달성 조건, 완료와 철회 조건은 프로젝트 헌장을 정본으로 삼는다.

| 산출물 | 비고 |
| --- | --- |
| ADR(Architecture Decision Record) | `맥락` 절에 기대는 전제를 한 문장으로 적고, 그 전제가 있는 프로젝트 헌장의 단락을 링크한다. |
| 요구사항 명세서 | 요구 ID와 단계별 요구사항을 정의한다. 「범위」와 「개발 단계」를 요구사항으로 구체화하고, 프로젝트 헌장과 값이 겹치는 항목은 프로젝트 헌장을 가리킨다. |
| 프로세스 목록 | 「범위」의 영역별로 프로세스를 나열하고, 프로세스마다 개발 단계를 배정한다. |
| 프로세스 설계서 | 프로세스 목록에 있는 프로세스마다 사용자와 시스템의 처리 흐름을 정의한다. |
| 화면 목록 | 화면을 나열하고, 화면마다 개발 단계를 배정한다. |
| 화면 설계서 | 화면 목록에 있는 화면마다 구성과 화면 간 이동을 정의한다. 지원 환경은 「규모와 제약」을 따른다. |
| 메뉴 목록 | 서비스의 메뉴 구조와 메뉴별로 연결되는 화면을 정의한다. 블로그 주인이 설정하는 블로그 메뉴(「범위」의 분류 영역)와는 구분한다. |
| 아키텍처 설계서 | 「규모와 제약」을 품질 목표와 제약의 근거로 사용하고, 구조마다 그 결정을 담은 ADR을 가리킨다. 「다음 프로젝트 헌장으로 넘기는 범위」까지 고려해서 설계한다. |
| RDB 스키마 | 프로젝트 헌장의 「규모와 제약」 절을 근거로 삼아 규모와 설계 판단을 한다. |

비용 한도는 이 프로젝트 헌장을 정본으로 삼는다. 다른 산출물에서는 비용 한도를 다시 적지 않고 이 헌장을 가리킨다.

본 프로젝트 헌장은 `active`로 전환한 날부터 프로젝트의 공식적인 기준선(Baseline)으로서 효력을 발휘한다. 정식 개발 사이클은 이 헌장부터 시작하며 이 전환일이 곧 전체 프로젝트 일정의 설계 단계 착수일이 된다.

프로젝트 헌장은 원칙적으로 수정하지 않는다. 단, 프로젝트의 핵심 목적, 제약 사항 또는 기준 범위에 중대한 변경이 불가피한 경우에 한하여 예외적으로 개정한다. 헌장을 개정할 때는 「변경 이력」에 날짜와 변경된 절을 명시하며, 헌장의 전제가 바뀜에 따라 영향을 받는 기존 ADR은 모두 재검토하여 필요 시 바뀐 전제에 기대는 새 기록으로 대체한다.

## 목적 {#purpose}

목적은 다음 세 가지이다.

| 목적 | 뜻 | 결과 |
| --- | --- | --- |
| 직접 사용한다. | 개발 노트를 이 엔진에서 쓰고 어디서나 읽는다. | `docs.the2davi.dev`를 내리면서 기존 글 221편을 옮겨온다. |
| 만들면서 배운다. | 규모가 큰 서비스에서 사용하는 구조를 실사용 규모에 맞춰 직접 만든다. | 별도의 달성 조건을 두지 않는다. 구현 방법을 고르는 기준으로 쓴다. |
| 보여준다. | 설계 판단과 개발 코드를 오픈소스로 공개한다. | 블록 편집기, 이력 그래프, 회원 서비스 분리가 서비스 엔진에서 돌아가며, 각각의 판단과 변경 이력을 산출물로 작성한다. |

목적이 서로 부딪히는 경우 다음 순서로 판단한다.

1. 개발 단계의 달성 조건에 도달하지 못하게 만드는 선택은 하지 않는다.
2. 그 안에서 구현 방법을 고를 때는 배우는 쪽을 고른다.
3. 보여주기 위해 범위를 넓히지 않는다. 범위를 넓히려면 프로젝트 헌장을 먼저 고친다.

## 개발 단계 {#phases}

| 단계 | 달성 조건 |
| --- | --- |
| 설계 | 요구사항 명세서·프로세스 목록·화면 목록·메뉴 목록 작성, 0단계에 필요한 ADR `accepted` 전환, 0단계 범위의 설계서 작성 |
| 0 | 가입·로그인 후 빈 화면 노출, 커밋-푸시 후 검증·배포 파이프라인 자동 수행 |
| 1 | 글 작성·발행 후 다른 브라우저에서 조회 가능, 저장할 때마다 편집 이력이 쌓이며 이전 저장점의 내용을 다시 조회 가능, 자동 백업이 돌고 백업에서 복구한 데이터로 같은 글을 다시 조회 가능 |
| 2 | 글에 미디어를 게시 및 첨부 |
| 3 | 편집 화면에서 블록을 옮기고 보관하고 꺼내고 유형을 변경 |
| 4 | 편집 이력을 그래프로 조회, 갈래를 분할하고 병합 |
| 5 | SEO 설정과 블로그 내 검색 제공, 기존 VitePress 글 221편 이전, `docs.the2davi.dev` 내림 |
| 6 | 소셜 로그인, 계정별 블로그 개설 |
| 7 | 한 계정의 블로그에 적용시킬 커스텀 테마·말머리·메뉴 설정이 저장 및 반영됨 |
| 8 | 여러 블로그를 아우르는 통합 검색, 사용자 찾기, 언어별 검색 제공, 언어별로 번역된 웹사이트 제공 |

설계 단계는 이 헌장이 발효된 날 시작한다. 이후 단계는 이전 단계의 달성 조건을 채운 날 시작한다. 1단계부터는 그 단계에 필요한 ADR과 설계서를 구현보다 먼저 작성한다. 각 단계의 시작일과 달성일은 저장소 README의 「단계」 표에 기록한다. 헌장은 범위나 전제가 바뀔 때만 고치기 때문에, 진행 기록은 헌장 밖에서 관리한다.

5단계의 *내림*은 `docs.the2davi.dev`에서 본문 제공을 중단하고, 옛 주소로 들어온 요청을 새 주소로 넘겨주는 상태로 전환하는 것을 말한다. 넘겨주기는 검색 엔진이 영구 이전으로 인식하는 방식을 사용하고, 5단계 달성 이후에도 최소 1년은 유지한다. 옛 호스트를 무엇으로 유지할지는 5단계 착수 전에 ADR에서 결정한다.

## 이해관계자 {#stakeholders}

| 이해관계자 | 기대하는 것 |
| --- | --- |
| 운영자 | 개발과 운영과 결정을 담당한다. |
| 방문자 | 로그인 없이 글을 읽는다. |
| 사용자 | 6단계부터 각자의 블로그를 개설하고 글을 쓴다. 「규모와 제약」의 규모 기준은 이 대상을 근거로 삼는다. |
| 개발자 | 돌아가는 서비스와 공개된 ADR로 설계 판단을 확인한다. |
| `the2davi.dev`의 후속 서비스 | 같은 회원 기반으로 로그인하고 회원 이벤트를 구독한다. |

마지막 항목은 사람이 아니지만 명시한다. 회원 관리 API를 MSA(Microservice Architecture)로 분리하고 이벤트 구독 방식으로 연결하는 구조의 근거 절반이 이 대상이며, 이 구조를 다루는 ADR은 이 전제에 기댄다. 아직 존재하지 않는 서비스이므로 이 항목은 가정으로 취급하고, 가정이 바뀌면 이 전제에 기댄 ADR을 다시 검토한다.

## 규모와 제약 {#scale-and-constraints}

| 항목 | 값 |
| --- | --- |
| 규모 | 실사용 계정 열 개 안팎. 지인과 가족 범위를 기준으로 삼는다. |
| 기준 데이터 | 현행 블로그 실측값. 글 221편, 카테고리 깊이 3단, 코드 블록 3,086개, 이미지 참조 161개. |
| 원칙 | 상용 서비스의 구조를 따르되 규모는 실사용 수준에 맞춘다. |
| 구조 | 회원 관리 API는 MSA로 분리하고, 블로그 서비스는 회원 이벤트를 구독한다. 이벤트 전달은 Kafka 같은 오픈소스 메시지 브로커 없이 코드로 직접 구현하고, 회원 테이블의 사본을 블로그 쪽 DB에 복사해 두는 방식을 사용한다. |
| 비용 | 월 운영 비용 KRW 50,000 미만. 외화로 청구되는 비용은 부가세를 포함해서 원화로 환산한 금액으로 판단한다. |
| 가용성 | 배포와 장애로 서비스가 중단되는 것을 감수한다. 이중화와 무중단 배포는 하지 않는다. |
| 사람 | 1인 개발. 본업 외 시간을 쓴다. |
| 일정 | 날짜를 두지 않고, 개발 단계의 순서와 시작 조건, 달성 조건으로 대신한다. 시작 조건은 「개발 단계」에 적는다. |
| 언어 | 한국어를 기본으로 한다. 한글 조합 입력과 한국어 검색을 전제로 설계한다. 언어별로 번역된 웹사이트와 언어별 검색을 제공하고, 지원할 언어와 번역 범위는 요구사항 명세서에서 정의한다. 주소 체계와 화면 문구는 처음부터 여러 언어를 고려해서 설계한다. |
| 지원 환경 | 최근 두 판본의 주요 브라우저. 좁은 화면의 읽기까지 반응형 웹으로 제공하며, 전용 앱은 만들지 않는다. |
| 개인정보 | 다른 계정을 받는 시점은 6단계다. 그 전까지 이 서비스가 보관하는 개인정보는 운영자 본인의 계정 정보뿐이다. |

*상용 서비스의 구조를 따른다*는 말은 규모가 큰 서비스에서 사용하는 구조를 작게나마 실제로 구현한다는 뜻이다. 회원 관리 API의 MSA 분리와 이벤트 구독 방식은 이 원칙에 따라 확정한 구조이다. 다만 메시지 브로커를 따로 띄우면 서버 리소스가 부족해질 수 있기 때문에, 이벤트 전달을 코드로 직접 구현하고 두 DB 사이에 테이블 사본을 복사하는 방식으로 서버 리소스 부족 리스크를 완화한다. 세부 구현 방식은 ADR에서 결정한다.

*규모는 실사용 수준에 맞춘다*는 말은 sharding, multi-region 배포, 대규모 트래픽 대비에 시간을 쏟지 않겠다는 뜻이며, 데이터 설계에도 같은 기준을 적용한다. 실측 규모에서 이득이 없는 색인과 구조는 선택하지 않는다. 불필요한 확장성 설계에 시간을 태우지 않는다.

비용은 제약이며, 그 한도 내에서 무엇을 어떻게 올릴지는 ADR에서 조사와 추산을 거쳐 확정한다. (미결: 클라우드 제공자와 1차 배포 구성.)

1단계를 달성하면 이 서비스에서 글을 작성할 수 있고, 그 이후에 작성한 글은 이 서비스에만 존재하게 된다. 5단계부터는 기존 글 221편의 유일한 보관처가 된다. 따라서 자동 백업과 복구 확인은 1단계 달성 조건에 포함한다.

## 범위 {#scope}

### 현재 프로젝트 헌장에서 제시하는 범위 {#in-scope}

| 영역 | 내용 | 단계 |
| --- | --- | --- |
| 계정과 인증 | 로그인과 계정 보호, 회원 관리, 소셜 로그인 | 0 · 6 |
| 글 작성 | 블록 단위 텍스트 에디터, 저장과 발행, 자동 저장 | 1 |
| 블록 | 텍스트 계열, 미디어 계열, 인용, 원본 HTML | 1 · 2 · 5 |
| 글과 메타데이터 | 글의 속성, 공개 상태, 문서 종류, SEO | 1 · 5 |
| 분류 | 카테고리, 섹션, 태그, 시리즈, 말머리, 메뉴와 그 계층 조작 | 1 · 3 · 7 |
| 블로그 | 계정마다 블로그 개설, 주소와 기본 설정 | 6 |
| 미디어 | 이미지, GIF, 동영상, 파일, 링크 카드, 썸네일 | 2 |
| 임시보관 | 블록을 빼 두었다가 다른 글에서도 꺼내 쓴다. | 3 |
| 이력 | 저장 이력을 쌓고, 그래프로 보고, 갈래를 나누고 합친다. | 1 · 4 |
| 인용 | 같은 블로그의 다른 글을 블록으로 끌어온다. | 5 |
| 읽기 화면 | 목록, 글, 태그, 시리즈 이동, 사이드바 여닫기, 본문 폭 조절, 이미지 확대 | 1 · 2 · 7 |
| 커스텀 테마 | 색, 글꼴, 레이아웃을 계정마다 저장하고 반영한다. | 7 |
| 검색 | 블로그 내 검색 | 5 |
| 통합 검색 | 여러 블로그를 아우르는 검색, 사용자 찾기, 언어별 검색 | 8 |
| 다국어 | 언어별로 번역된 웹사이트 제공 | 8 |

### 제외 범위 {#out-of-scope}

| 임의 템플릿 업로드 | 템플릿 엔진은 표현식 실행 경로를 포함하므로 앞 항목과 같은 위험을 가진다. | 없음. |
| 결제와 구독 | 지인과 가족에게 무상으로 제공하는 서비스라 과금 대상이 없다. 결제는 정산·환불·세무 처리 의무를 함께 가져온다. | 서비스를 유상으로 전환할 일이 있을 때. |
| 대규모 트래픽 대비 | 설계 기준 규모가 실사용 계정 열 개 안팎이다. 이 규모에서 캐시 계층·수평 확장·샤딩은 얻는 성능보다 운영 복잡도를 더 늘린다. | 「규모와 제약」의 규모 기준을 상향할 때. |
| 여러 사용자의 실시간 동시 편집 | 동시 편집은 CRDT(Conflict-free Replicated Data Type) 또는 OT(Operational Transformation) 기반의 충돌 해소 계층을 문서 모델 아래에 요구한다. 이번 범위는 편집 이력 그래프를 세우는 데까지로 한다. 같은 사용자가 탭을 여럿 연 경우는 충돌 감지로 처리한다. | 다중 사용자 협업을 개발 범위에 넣을 때. |
| 블록 내부 텍스트의 자동 병합 | 같은 블록을 양쪽에서 수정한 경우 충돌로 표시하고 사용자가 선택하게 한다. 문자 단위 자동 병합은 앞 항목과 같은 기반을 요구한다. | 다중 사용자 협업을 개발 범위에 넣을 때. |

| 동영상 스트리밍 변환 및 자막 | 트랜스코딩(transcoding)과 자막 처리는 별도 처리 파이프라인과 저장·전송 비용을 요구한다. 업로드한 원본을 브라우저 기본 재생기로 재생하는 데까지 한다. | 비용 한도 안에서 외부 서비스로 대체가 가능할 때. |
| 모바일 앱 | 읽기와 쓰기 모두 반응형 웹으로 제공한다. 네이티브 앱은 스토어 심사와 두 벌의 클라이언트 유지 비용을 가져온다. | 웹으로 해결되지 않는 요구가 확인될 때. |

| --- | --- | --- |

## 완료와 철회 {#closing-conditions}

이 헌장은 `proposed` 상태로 작성하고, 실제 효력을 발휘하는 날 `active`로 변경한다.

프로젝트 헌장은 8단계 달성 조건을 채운 날 `completed`로 닫는다. 남은 기능은 「다음 프로젝트 헌장으로 넘기는 범위」를 근거로 후속 헌장에서 다룬다.

5단계 이후에 진행을 멈추기로 하는 경우, 남은 단계를 범위에서 덜어 내는 변경을 거친 뒤 `completed`로 닫는다. 직접 사용한다는 목적이 5단계에서 달성되기 때문이다.

5단계에 도달하기 전에 중단하기로 하는 경우에는 `withdrawn`으로 닫고 사유를 기록한다.

목적이 바뀌어서 이 헌장의 전제가 더는 맞지 않는 경우에는 새 헌장을 열고, 이 헌장은 `superseded`로 닫는다. 이때 새 헌장의 `supersedes`와 이 헌장의 `superseded_by`에 서로의 ID를 적는다.

닫을 때는 목적 세 가지가 어디까지 달성되었는지를 이 문서 끝에 한 문단으로 기록한다.
