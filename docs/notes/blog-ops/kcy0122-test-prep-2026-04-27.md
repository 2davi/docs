## 0. 본 가이드 사용법

### 0.1 누구를 위한 무엇인가

본 문서는 **kcy0122(김찬영)이 2026-04-27 STN 사전 단계에서 단독으로 따라할 수 있도록 설계된 step-by-step 매뉴얼**이다. 핸드북 챕터 03·05·08·09에 흩어진 정찰·격자·체크리스트를 6개 영역(VM Network, VM Storage, VM Operations, Node Disk, Node Network, Datacenter Storage)의 21개 시나리오로 추출하여, GUI 클릭·CLI 명령·검증 출력을 한 화면에서 따라갈 수 있는 형태로 묶었다.

본 가이드의 모든 시나리오는 다음 두 조건을 충족한다.

1. **격자 L1×R1 ~ L4×R2 안에 머문다** — 자기 자원·자기 노드 영향 시나리오부터 클러스터 전체 변경(storage.cfg 추가) 시나리오까지 다루되, **격자가 높을수록 격리 절차(단일 노드 nodes 제약, 빈 디스크/인터페이스 사전 식별, staging-apply 분리)가 강화**된다. L4×R3 이상 영역은 STN 본번에서 권한자 동석 하에서만 진행.
2. **CMP UI에서 만든 것이 실제 PVE 상태에 반영되었는지 6 Layer로 검증한다** — UI 단순 표시가 아니라 PVE 설정 파일·5노드 동기화·게스트 사용 가능성까지 사슬을 끝까지 돌린다.

### 0.2 본 가이드와 핸드북의 관계

| 본 가이드 § | 핸드북 참조 |
| --- | --- |
| §1 사전 준비 | 09 §2 STAGE 1·2 (사전 점검 체크리스트) |
| §2 검증 사슬 | 00 §3 정찰 철학(Blast Radius × Reversibility) |
| §3 VM Network | 05 §4.1 CRUD·§4.4 클러스터 일관성 |
| §4 VM Storage | 03 §4.1·§4.2 + 06 §2 VM 인벤토리 |
| §5 VM Operations (마이그레이션) | 06 §2 + 08 §2.2 |
| §6 Node Disk | 03 §2 정찰 + §4 시나리오 |
| §7 Datacenter Storage | 04 §3 의제 회의 결과 (회의 후 갱신) |
| §8 Node Network | 05 §2 정찰 + §3 비정상 패턴 + §4 CRUD |

본 가이드는 핸드북을 **대체하지 않는다**. 막히면 핸드북의 해당 챕터를 펼치고, 본 가이드는 실행 흐름의 가이드로만 활용한다.

### 0.3 4 영역의 격자 분류와 처리 방침

본 가이드는 **L1×R1 ~ L4×R2** 영역을 모두 다룬다. 격자가 높을수록 사전 검증·격리·되돌리기 절차가 강화된다. **L4×R3 이상(금지)·L5(절대금지) 영역은 본 가이드에서 다루지 않으며 STN 본번에서 권한자 동석 하에서만 진행**한다.

| 영역 | 대표 작업 | 격자 | 본 가이드 처리 |
| --- | --- | --- | --- |
| **A. VM Network** | NIC add/edit/remove, VM 방화벽 | L1×R1 | 4 시나리오 (전 케이스 변경 가능) |
| **B. VM Storage** | 디스크 add/resize/move | L1×R1 ~ L2×R2 | 3 시나리오 (move-disk만 L2×R2) |
| **C. VM Operations** | VM 마이그레이션 (live/offline) | L2×R2 | 1 시나리오 (노드 간 라이브 마이그) |
| **D. Node Disk** | LVM VG/Thinpool/ZFS pool 생성, Directory 생성 | L3×R1 ~ L3×R2 | 정찰 2 + 변경 4 시나리오 (빈 디스크에 한정) |
| **E. Node Network** | 신규 bridge·VLAN 추가 | L3×R1 ~ L3×R2 | 정찰 4 + 변경 2 시나리오 (빈 bridge·sub-interface 한정) |
| **F. Datacenter Storage** | storage.cfg CRUD (NFS/SMB/iSCSI/Directory/ZFS) | L4×R1 ~ L4×R2 | 5 시나리오 (단일 노드 제약 + 비활성 토글 활용) |

격자 한도별 추가 안전 절차:

- **L3 영역(C·D·E의 변경)**: 작업 노드를 단일로 격리(`pve-nd03` 권장), **수정 대상 디스크·인터페이스가 아무 자원도 점유하지 않는 빈 자원**임을 §1 사전 정찰에서 확인 후 진입.
- **L4 영역(F + Datacenter 옵션 변경)**: `nodes` 필드로 단일 노드 격리, 변경은 **disable→edit→enable 또는 추가→사용→삭제 사이클로 R1 가역성 확보**, 5노드 pmxcfs 동기 검증을 베이스라인·사후 두 번 수행.
- **R2 영역**: 백업·스냅샷 또는 명시적 cleanup 절차가 사전에 준비되어 있어야 진입(즉시 가역이 아님).

### 0.4 본 가이드의 한계

- **회의(2026-04-27) 결과 반영 전 작성본**이다. 챕터 04 협의 회의에서 자원명 prefix·VMID 대역·평면 이전이 합의되면 본 가이드의 §1.1 격리 규약이 갱신될 수 있다.
- **kcy0122의 PVE 권한 수준에 의존**한다. PVE WebUI `admin@pve` 또는 `root@pam` 권한이 가정되며, L3·L4 시나리오는 root SSH가 필요하다(§1.2 사전 점검에서 검증).
- **실제 데이터를 수정하지 않는 정찰 명령은 모든 테스터가 안전**하지만, 변경 명령(L3·L4)은 본 가이드의 §1.1 격리 규약 + 시나리오별 사전 정찰을 빠짐없이 거쳤을 때만 안전하다.
- **L3·L4 시나리오는 결과의 5노드 동기 전파를 일으키므로 "본인이 의도하지 않은 다른 변경이 동시에 일어났는가"를 §8 사후 검증에서 반드시 확인**한다 — 동시 작업 중인 다른 테스터의 변경과 본인 변경이 섞이면 결함 책임 추적이 무너진다.

### 1.2 진입 정찰 5분 (핸드북 09 §2 STAGE 2 축약본)

CMP UI 접속 전 SSH로 클러스터 건강성 + 본인 작업 영역 비어있음을 확인한다. **이 단계가 실패하면 테스트를 시작하지 않는다.**

#### 1.2.1 클러스터 건강성

```bash
# nd01(jump host) 또는 nd03 SSH 후 실행
pvecm status | grep -E 'Quorate|Total votes|Expected'
# 기대: Quorate: Yes, Expected/Total votes: 5

ha-manager status
# 기대: quorum OK, master 1대, lrm 5대 active

for n in pve-nd0{1..5}; do
  echo "=== $n ==="
  ssh "$n" "uptime | awk -F'load average: ' '{print \$2}'"
done
# 기대: 모든 노드 응답 + load < 5
```

#### 1.2.2 P0 항목 사전 확인

```bash
# nd02의 vmbr2 속도 (100 Mbps 이슈 잔존 확인)
ssh pve-nd02 "ethtool enp10s0 2>/dev/null | grep Speed"
# 기대: 2.5Gb/s (정비 완료 시) 또는 100Mb/s (P0 미해결)
# 100Mb/s면 → §6 D1에서 nd02를 nodes 제약에서 반드시 제외

# 5노드 ERROR 로그 베이스라인
for n in pve-nd0{1..5}; do
  cnt=$(ssh "$n" "journalctl --since '5 minutes ago' -p err --no-pager 2>/dev/null | wc -l")
  echo "[$n] ERROR last 5min: $cnt"
done
# 기대: 본인 작업 시작 전이므로 baseline. 테스트 후 비교 기준
```

#### 1.2.3 본인 권한 확인

### 1.3 베이스라인 박제 (필수)

테스트가 끝났을 때 "내가 만든 것 외에 다른 변경이 있는가"를 비교할 기준점이다.

```bash
# 작업 디렉토리
mkdir -p /tmp/kcy0122-2026-04-27 && cd /tmp/kcy0122-2026-04-27

# 1. pmxcfs 동기 파일 5노드 md5 (이게 변하면 클러스터 영향 발생)
for n in pve-nd0{1..5}; do
  echo "=== $n ==="
  ssh "$n" "md5sum /etc/pve/storage.cfg /etc/pve/firewall/cluster.fw 2>/dev/null"
done > baseline-pmxcfs.txt

# 2. 작업 노드의 디스크·네트워크 상태
ssh pve-nd03 "
  echo '--- lsblk ---'; lsblk
  echo '--- pvs ---'; pvs
  echo '--- vgs ---'; vgs
  echo '--- lvs ---'; lvs
  echo '--- ip a ---'; ip a
  echo '--- brctl show ---'; brctl show
  echo '--- iscsiadm sessions ---'; iscsiadm -m session 2>/dev/null
" > baseline-nd03.txt

# 3. 클러스터 자원 인벤토리
pvesh get /cluster/resources --output-format json > baseline-resources.json
qm list > baseline-vms.txt
pvesh get /storage --output-format json | jq -r '.[] | "\(.storage)\t\(.type)\t\(.content)"' > baseline-storages.txt

# 4. 본인 VMID 대역 비어있음 확인
qm list | awk '$1>=113000 && $1<=113099 {print}'
# 기대: 출력 없음. 무언가 출력되면 §1.4에서 본인 자원인지 검증
```

테스트 종료 후 동일 명령으로 새 결과 만든 뒤 `diff baseline-* new-*`로 비교한다. **자기가 의도한 변경 외의 차이가 발견되면 보고**한다.

### 1.4 테스트용 VM 113001 준비

본 가이드의 모든 시나리오는 **테스트용 VM 한 대를 기준**으로 진행된다. 이미 본인이 가지고 있는 VM이 있으면 옵션 A, 새로 만들면 옵션 B.

#### 1.4.1 옵션 A: 기존 본인 VM 사용

베이스라인의 `qm list` 결과 중 본인이 작성자임을 확신할 수 있는 VM을 식별한다. 확신 기준:

- VMID가 본인이 만든 것
- 이름에 `kcy`, `kim`, 본인이 사용한 prefix 포함
- 또는 본인이 직접 생성한 기억이 있는 자원

확신이 안 서면 옵션 B로 간다. **다른 테스터의 자원을 본 가이드의 시나리오 대상으로 삼지 않는다** (핸드북 §3.4 — 다른 테스터 자원 변경은 L4 이상).

본 가이드는 식별된 VM의 VMID를 `113001`로 가정하고 명령을 작성한다. 실제 VMID가 다르면 모든 명령에서 `113001`을 본인 VMID로 치환한다.

#### 1.4.2 옵션 B: 새 VM 113001 생성 (권장)

깨끗한 베이스라인을 만들기 위해 새 VM을 만든다.

##### CMP UI 동작 (5분)

1. CMP 좌측 메뉴 → **가상머신** → 우상단 **+ 가상머신 생성** 또는 **상단 공통메뉴 가상머신 생성** (UI-VM0100-01)
2. **일반** 탭
   - 노드: `pve-nd03`
   - VM ID: `113001`
   - 이름: `kcy0122-test-vm-01`
3. **OS** 탭
   - 매체: **이미지 파일을 사용하지 않음** (또는 이미 업로드된 ISO 선택 — 가능하면 ubuntu/cirrus 같은 작은 이미지)
   - 게스트 OS 종류: Linux 6.x - 2.6 커널
4. **시스템** 탭
   - 그래픽 카드: 기본
   - 머신: 기본
   - BIOS: 기본 (SeaBIOS)
   - SCSI 컨트롤러: VirtIO SCSI single
5. **디스크** 탭
   - Bus/장치: SCSI 0
   - 스토리지: `local-zfs` (작업 노드인 nd03의 로컬 zpool)
   - 디스크 크기 (GiB): `8`
6. **CPU** 탭
   - 코어: 1
   - 종류: x86-64-v2-AES (기본)
7. **메모리** 탭
   - 메모리 (MiB): `1024`
8. **네트워크** 탭
   - 브리지: `vmbr1` (VM 평면 — 핸드북 권장 분리)
   - 모델: VirtIO (반가상화)
9. **확인** 탭 → **완료** 클릭

- "완료" 클릭 시 호출되는 요청 캡처

- 페이로드를 별도 메모(`/tmp/kcy0122-2026-04-27/devtools-vm-create.txt`)에 저장

## 2. 검증 사슬 6 Layer (모든 시나리오에 일괄 적용)

본 가이드의 모든 시나리오는 다음 6단계를 빠짐없이 거친다. 이 사슬이 김찬영 보고서가 다른 테스터와 차별화되는 결정적 차이가 된다.

```text
[L1] CMP UI 동작 → 결과 표시 확인
        ↓
[L2] CMP DevTools Network 탭 → API 페이로드·응답 캡처
        ↓ "CMP가 자기 입으로 무엇을 했다고 주장하는가"
[L3] PVE REST API 직접 조회 (CMP 우회)
        ↓ pvesh get / curl https://pve-nd03:8006/api2/...
[L4] PVE 설정 파일 직접 확인
        ↓ /etc/pve/storage.cfg, /etc/pve/qemu-server/{vmid}.conf,
        ↓ /etc/network/interfaces, /etc/pve/firewall/{vmid|cluster}.fw
[L5] 5노드 동기화 검증 (pmxcfs 분기)
        ↓ ssh 일괄로 md5 비교
[L6] 실제 사용 가능성 (게스트 OS / 호스트 mount / ping / I/O)
```

### 2.1 Layer별 명령 패턴

```bash

# F12 → Network → 작업 클릭 → 요청 우클릭 → Copy as cURL
# 응답 본문은 별도 저장: /tmp/kcy0122-2026-04-27/{시나리오ID}-L2.txt

# ── L3: PVE API 직접 ────────────────────────────────────
pvesh get /nodes/pve-nd03/qemu/113001/config        # VM config
pvesh get /storage                                   # storage list
pvesh get /nodes/pve-nd03/network                    # node network
pvesh get /nodes/pve-nd03/disks/list                 # node disks
pvesh get /cluster/firewall/options                  # cluster firewall

# ── L4: 설정 파일 직접 ─────────────────────────────────
ssh pve-nd03 "cat /etc/pve/qemu-server/113001.conf"
ssh pve-nd03 "cat /etc/pve/storage.cfg"
ssh pve-nd03 "cat /etc/network/interfaces"           # ★ 노드별, pmxcfs 동기 안 됨
ssh pve-nd03 "cat /etc/pve/firewall/113001.fw"       # VM firewall

# ── L5: 5노드 동기화 ──────────────────────────────────
for n in pve-nd0{1..5}; do
  ssh "$n" "md5sum /etc/pve/storage.cfg" 2>&1
done
# storage.cfg, /etc/pve/firewall/, /etc/pve/datacenter.cfg 는 모두 동일해야 함
# /etc/pve/qemu-server/{vmid}.conf 는 VM 호스팅 노드에만 존재

# ── L6: 실제 사용 (시나리오별 다름, 각 §에서 명시) ────
```

### 3.2 VM-N2. NIC 모델 교체 (virtio ↔ e1000) (L1×R1, 20분)

#### 시나리오 의의

같은 NIC을 model만 바꾸는 변경이다. 호스트 측 tap은 이름이 동일하지만 게스트 입장에선 **완전히 다른 PCI 디바이스**로 인식된다. Linux predictable naming이 인터페이스 이름을 바꿀 수 있다(`ens18` → `ens19`).

#### 사전

```bash
ssh pve-nd03 "qm config 113001 | grep ^net0"
# 기대: net0: virtio=...,bridge=vmbr1
# (또는 N1을 net1으로 진행했다면 net1을 대상으로)
```

게스트 SSH 접속 후 현재 인터페이스 이름 기록:

```bash
# 게스트에서
ip -br link show | grep -v lo
# 예: ens18  UP  XX:XX:XX:XX:XX:XX
```

#### CMP UI 동작

1. CMP UI → 113001 → 하드웨어 → `net0` 더블클릭(또는 선택 후 편집)
2. 모델: `VirtIO (반가상화)` → `Intel E1000`으로 변경
3. **확인** 또는 **OK**

##### DevTools

- 기대 API: `PUT /api2/json/nodes/pve-nd03/qemu/113001/config`
- 페이로드: `{ "net0": "e1000=XX:XX:XX:XX:XX:XX,bridge=vmbr1" }`

```bash
pvesh get /nodes/pve-nd03/qemu/113001/config | grep ^net0

# 기대: 위와 동일
```

#### Layer 6: 게스트 인식 (재부팅 필요)

NIC 모델 교체는 **hotplug 불가능**한 변경이다. CMP UI는 변경을 즉시 표시하지만, 실제 게스트는 재부팅 전까지 이전 모델로 동작한다.

```bash
# CMP UI에서 113001 → 더보기 → 정지(shutdown) → 시작(start)
# 또는 CLI:
ssh pve-nd03 "qm shutdown 113001 && sleep 10 && qm start 113001"
```

게스트 부팅 후:

```bash
# 게스트 dmesg에서 NIC 등장 로그
sudo dmesg | grep -iE 'e1000|virtio.*ether'
# 기대: e1000 driver 로드 메시지

# 새 인터페이스 이름 (predictable naming 변동 가능성)
ip -br link show | grep -v lo
# 가능성 1: 같은 ens18 (MAC이 동일하면 udev rule이 같은 이름 부여)
# 가능성 2: ens19 또는 다른 이름 (predictable naming 변경)
```

#### 결함 후보

- model 변경 후 게스트가 NIC을 인식 못 함 → CMP가 페이로드를 잘못 보냈거나 PVE가 hotplug를 시도하다 실패
- 게스트 부팅 시 IP 받지 못함 → udev rule이 옛 인터페이스 이름에 박혀있어 새 NIC을 무시
- DevTools 페이로드는 `e1000`인데 PVE 설정 파일은 여전히 `virtio` (CMP 캐시 결함)

#### 되돌리기

UI에서 모델을 다시 `VirtIO (반가상화)` → 게스트 재부팅 → 원상복귀 확인.

### 3.3 VM-N3. NIC bridge 변경 (vmbr1 → vmbr0 → 복귀) (L1×R1, 20분)

#### 위험 안내

본 시나리오는 게스트가 **mgmt 평면(vmbr0)에 연결**되는 상태를 일시적으로 만든다. 핸드북 §2.5에서 "14 VM이 mgmt 평면 NIC 사용 = 평면 분리 설계 운영 붕괴"로 플래그된 패턴이다. **테스트 종료 시 즉시 vmbr1로 복귀**해야 한다 (R1 — 즉시 가역).

#### 단계

1. CMP UI → 113001 → 하드웨어 → net0 편집 → 브리지 `vmbr1` → `vmbr0` → 확인
2. DevTools 캡처: `PUT .../config`, 페이로드 `{ "net0": "...,bridge=vmbr0" }`
3. PVE 검증:
   ```bash
   pvesh get /nodes/pve-nd03/qemu/113001/config | grep ^net0
   ssh pve-nd03 "brctl show vmbr0 | grep tap113001"   # vmbr0에 tap 등장

   ```
4. 게스트에서:
   ```bash
   sudo dhclient -r ens18   # 기존 IP 해제
   sudo dhclient ens18      # 새 평면에서 IP 받기
   ip a show ens18
   # 기대: 10.99.10.X (mgmt 평면)
   ```
5. 평면 침범 검증 (이게 핵심):
   ```bash
   # 게스트에서
   ping -c 3 10.99.10.16   # TrueNAS mgmt 평면
   # 응답 오면 → 평면 침범 확인 (의도된 분리 무력화 증명)
   ```

#### 즉시 복귀

```text
CMP UI → 113001 → 하드웨어 → net0 편집 → 브리지 vmbr0 → vmbr1 → 확인
게스트: dhclient -r ens18 && dhclient ens18 → IP가 10.99.40.X로 복귀
```

#### 결함 후보

- bridge 변경 후 `brctl show`에서 tap이 양쪽 bridge에 모두 등장 (orphan)
- DevTools 페이로드가 `vmbr0`인데 PVE 설정은 `vmbr1` 그대로 (CMP 캐시·동기 결함)
- 게스트 IP 변경 없이 표면적으로만 변경됨 (실제 트래픽 평면은 그대로)

### 3.4 VM-N4. VM 방화벽 규칙 추가 (L1×R1, 30분)

```bash
# L3: PVE API
pvesh get /nodes/pve-nd03/qemu/113001/firewall/rules
# 기대: 두 규칙 (ACCEPT TCP 22, DROP Ping)

# L4: 설정 파일
ssh pve-nd03 "cat /etc/pve/firewall/113001.fw"
# 기대:
# [OPTIONS]
# enable: 1
#
# [RULES]
# IN ACCEPT -p tcp --dport 22 -i net0 ...
# IN DROP -macro Ping -i net0 ...

# L5: 5노드 동기화 (firewall 디렉토리는 pmxcfs 동기)
for n in pve-nd0{1..5}; do
  ssh "$n" "md5sum /etc/pve/firewall/113001.fw 2>/dev/null"
done
# 기대: 5노드 모두 동일 md5 (또는 파일 존재만 확인)
```

#### Layer 6: 호스트 nftables/ebtables 박힘 + 외부 통신 검증

PVE 방화벽이 활성화된 직후 **호스트의 nftables 규칙**이 동적으로 생성된다.

```bash
# 호스트 nftables 규칙에서 113001 추적
ssh pve-nd03 "nft list ruleset | grep -i 'tap113001\|fwbr113001'"
# 기대: tap113001i0 또는 fwbr113001i0 매칭 규칙 출현

# 또는 ebtables (PVE는 fwbr 위에서 ebtables 사용)
ssh pve-nd03 "ebtables -L 2>/dev/null | grep -A5 'tap113001\|fwbr113001'"

# iptables 측에서도
ssh pve-nd03 "iptables -L PVEFW-tap113001i0-IN -n 2>/dev/null"
# 기대: ACCEPT tcp dpt:22 / DROP icmp 비슷한 규칙
```

외부에서 통신 시도:

```bash
# 다른 노드(예: nd04) SSH에서 게스트 IP로 접근
ssh pve-nd04 "ssh -o ConnectTimeout=5 root@10.99.40.150 'echo ok'"
# 기대: ok (SSH 22 ACCEPT 적용)

ssh pve-nd04 "ping -c 2 -W 2 10.99.40.150"
# 기대: 0 received (Ping DROP 적용)
```

#### 결함 후보 (김찬영 스타일에 잘 맞음)

- UI에서 활성화 토글 ON했지만 nftables 규칙 미생성
- 규칙 추가는 됐지만 인터페이스 필터(`-i net0`)가 페이로드에 누락 → 모든 인터페이스에 적용
- DevTools 페이로드는 `enable: 1`인데 PVE 파일은 비어있음 (CMP 캐시)
- 5노드 중 일부에 firewall 디렉토리 동기 안 됨 (pmxcfs 분기)

#### 되돌리기

```text
CMP UI → 113001 → 방화벽 → 규칙 모두 선택 → 삭제
                       → 옵션 → 방화벽 활성화 OFF
```

검증:

```bash
ssh pve-nd03 "cat /etc/pve/firewall/113001.fw"
# 기대: enable: 0 또는 빈 [RULES]

ssh pve-nd03 "nft list ruleset | grep -c tap113001"
# 기대: 0 (또는 매우 적음)
```

## 4. VM Storage 시나리오 (영역 B — 보너스)

VM Network에 자신감이 붙은 후 진행. VM Storage는 디스크 자체가 자기 자원이라 L1×R1이지만, **move-disk(VM-S3)는 L2×R2** — 백업/스냅샷 가역 영역.

### 4.1 VM-S1. 디스크 추가 → 게스트 사용 (L1×R1, 40분)

#### 사전

```bash
ssh pve-nd03 "qm config 113001 | grep -E '^scsi|^virtio|^sata|^ide'"
# 기대: scsi0 1개만 (1.4에서 만든 베이스라인)
```

#### CMP UI

1. CMP UI → 113001 → 하드웨어 → **추가** → **하드디스크** (UI-VM0200-01)
2. 입력
   - Bus/장치: SCSI 1
   - 스토리지: `local-zfs`
   - 디스크 크기 (GiB): `1`
   - 캐시: 기본
   - 폐기(Discard): 체크 (선택)
   - SSD 에뮬레이션: 체크 (선택)
3. **추가** 클릭

#### DevTools

- 기대 API: `POST /api2/json/nodes/pve-nd03/qemu/113001/config`
- 페이로드: `{ "scsi1": "local-zfs:1,discard=on,ssd=1" }`

#### Layer 3-4 검증

```bash
pvesh get /nodes/pve-nd03/qemu/113001/config | grep '^scsi'
# 기대: scsi0, scsi1

ssh pve-nd03 "grep '^scsi' /etc/pve/qemu-server/113001.conf"
# 기대: 동일

# 백엔드 자원 (local-zfs는 zvol)
ssh pve-nd03 "zfs list | grep 113001"
# 기대: rpool/data/vm-113001-disk-0 (scsi0), vm-113001-disk-1 (scsi1)
```

#### Layer 6: 게스트 사용

```bash
# 게스트 SSH
sudo lsblk
# 기대: sda (기존 8G), sdb (신규 1G) — SCSI 컨트롤러 기준

# 파일시스템 + 마운트 + 쓰기
sudo mkfs.ext4 /dev/sdb
sudo mkdir -p /mnt/test
sudo mount /dev/sdb /mnt/test
echo "kcy0122 wrote here at $(date)" | sudo tee /mnt/test/marker.txt
sudo sync

# 호스트 측 데이터 박힘 확인
# - 게스트가 1G 디스크에 작성 → zvol 사용량 증가
exit  # 게스트 빠져나옴

ssh pve-nd03 "zfs list rpool/data/vm-113001-disk-1"
# USED 컬럼이 0보다 큰 값으로 변동 (실제 데이터 박힘 증명)
```

#### 결함 후보

- UI는 "디스크 추가됨" 표시하지만 zvol 미생성
- 게스트가 sdb를 인식 못 함 (CMP가 SCSI 컨트롤러 잘못 전달)
- 게스트가 작성한 데이터가 zvol USED에 반영 안 됨 (캐시 결함 의심)

#### 되돌리기

UI → scsi1 분리 → 삭제. zvol도 함께 삭제 확인:

```bash
ssh pve-nd03 "zfs list | grep 113001-disk-1 || echo 'OK: removed'"
```

zvol이 남아있으면 **orphan zvol** 결함. 핸드북 §2.7에서 VM 802가 만든 패턴.

---

### 4.2 VM-S2. 디스크 사이즈 조정 (resize) (L1×R1, 20분)

#### CMP UI

1. CMP UI → 113001 → 하드웨어 → `scsi0` 선택
2. 상단 **디스크 동작** → **크기 변경**
3. 증가량: `+2` GiB (1.4에서 8G로 만들었다면 → 10G)
4. **크기 변경** 클릭

#### DevTools

- 기대 API: `PUT /api2/json/nodes/pve-nd03/qemu/113001/resize`
- 페이로드: `{ "disk": "scsi0", "size": "+2G" }`

#### 검증

```bash
ssh pve-nd03 "qm config 113001 | grep ^scsi0"
# 기대: scsi0: local-zfs:vm-113001-disk-0,size=10G (size 변경)

ssh pve-nd03 "zfs list | grep 113001-disk-0"
# 기대: VOLSIZE 10G로 증가

# 게스트 측 — 게스트 OS는 자동 감지하지만 파일시스템 확장은 수동
# 게스트에서:
sudo lsblk
# /dev/sda 의 SIZE가 10G로 변동 (게스트가 SCSI 재스캔 자동 수행)

# 만약 lsblk에 그대로 8G 보이면:
sudo echo 1 | sudo tee /sys/class/block/sda/device/rescan
sudo lsblk

# 파일시스템 확장 (root partition인 경우)
sudo growpart /dev/sda 1   # cloud-utils 필요
sudo resize2fs /dev/sda1   # ext4
```

#### 결함 후보

- UI 표시 size 변경되었으나 zvol VOLSIZE는 그대로 (PVE API 호출 실패 캐시 결함)
- 게스트가 size 변경을 감지 못 함 (qemu-guest-agent 미설치 또는 hotplug 결함)
- size를 줄이려 시도 시 (`-1G`) 어떤 에러? — **자율 시도 금지**, 데이터 손실 위험

#### 되돌리기

PVE는 디스크 축소를 지원하지 않으므로 **resize는 일방향 가역**이다. R1로 보이지만 실제로는 R3에 가깝다 — 본 시나리오는 **+2G만 시도**, 줄이지 말 것.

### 4.3 VM-S3. 디스크 이동 (move-disk) (L2×R2, 60분)

#### 시나리오 의의

같은 VM의 디스크를 다른 storage로 이동. PVE가 백그라운드 복사를 수행하며, 진행 중 취소 시 양쪽 storage에 잔재(orphan)가 발생 가능.

**전제**: §6 D1에서 `kcy0122-nfs-test-01` storage가 등록되어 있다고 가정. 등록 전이면 본 시나리오 보류.

#### 사전

```bash
ssh pve-nd03 "qm config 113001 | grep ^scsi0"
# 기대: scsi0: local-zfs:vm-113001-disk-0,...

ssh pve-nd03 "zfs list | grep 113001-disk-0"
# 백엔드 zvol 위치 확인
```

#### CMP UI

1. CMP UI → 113001 → 하드웨어 → `scsi0` 선택
2. 상단 **디스크 동작** → **디스크 이동**
3. 입력
   - 대상 스토리지: `kcy0122-nfs-test-01`
   - 형식: 자동 (NFS이므로 qcow2)
   - **소스 삭제**: 체크 (이동이 끝나면 원본 zvol 삭제 — R1 스타일)
   - 또는 체크 해제 (양쪽에 모두 두는 분리 — orphan 검증용)
4. **이동** 클릭

#### Layer 1·2 — 진행 상황 캡처 (이게 결함 발견의 핵심)

- CMP UI 작업 이력에 진행 작업이 등장
- 진행률 % 표시
- DevTools에서 polling 요청 캡처:
  - `GET /api2/json/nodes/pve-nd03/tasks/{UPID}/status`
  - `GET .../log`
- 진행 중 **다른 화면으로 이동했다가 돌아왔을 때 진행률 표시 정확한가** → 김찬영의 UI 일관성 검증 영역

#### Layer 3-6 검증 (완료 후)

```bash
# L3-4
pvesh get /nodes/pve-nd03/qemu/113001/config | grep ^scsi0
# 기대: scsi0: kcy0122-nfs-test-01:113001/vm-113001-disk-0.qcow2,size=10G

# L4 백엔드 — 새 위치
ssh pve-nd03 "ls /mnt/pve/kcy0122-nfs-test-01/images/113001/"
# 기대: vm-113001-disk-0.qcow2 존재

# 원본 zvol — 소스 삭제 체크했다면 사라져야
ssh pve-nd03 "zfs list | grep 113001 || echo 'OK: source removed'"
# 기대: 출력 없음 (소스 삭제 시) 또는 zvol 잔존 (체크 해제 시 — 의도적 orphan)

# L5: storage.cfg 동기 (storage는 변경 없음, 이동만)
# scsi0 변경은 qemu-server 동기 — N1과 동일
```

#### 게스트 사용 가능성 (Layer 6)

```bash
# CMP UI → VM 시작 → VNC 또는 SSH
# 게스트 부팅 정상?
sudo lsblk
# 기대: sda 10G 그대로 (이동은 호스트 측 변화, 게스트는 영향 없음)

# 마커 파일 여전히 존재?
sudo mount /dev/sdb /mnt/test 2>/dev/null
ls /mnt/test/marker.txt
cat /mnt/test/marker.txt
# 기대: 4.1에서 작성한 내용 그대로
```

#### 결함 후보 — orphan 검증 (이게 핵심)

```bash
# 본 시나리오 후: 원본 zvol에 113001 자취
ssh pve-nd03 "zfs list | grep 113001"
# 1) "소스 삭제" 체크했는데 zvol 잔존 → orphan zvol 결함
# 2) 새 위치 .qcow2 사이즈가 zvol VOLSIZE보다 작음 → 데이터 손실
```

UI에서 작업 완료 표시되었는데 백엔드에 잔재 있으면 **김찬영의 4월 22일 스타일 결함 보고서 형식으로 정밀 보고**.

#### 되돌리기

같은 절차로 대상 → 원본(`local-zfs`)으로 다시 이동. **R2 영역** — 1G 데이터를 다시 옮기는 데 시간 소요. 시나리오 시작 전 백업 권장.

## 5. VM Operations 시나리오 (영역 C — 마이그레이션)

### 5.1 VM-M1. 본인 VM 노드 간 라이브 마이그레이션 (L2×R2, 60분)

#### 시나리오 의의

VM 113001을 `pve-nd03` → `pve-nd04`로 라이브 마이그레이션. CMP UI가 보고하는 마이그레이션 결과가 실제 PVE 클러스터에서 정상 종결되었는지, 그리고 게스트 측 다운타임이 발생했는지를 검증한다. 격자 L2(자기 VM 한정 + 두 노드 영향)·R2(되돌리기는 역방향 마이그레이션 필요).

라이브 마이그레이션은 **공유 storage가 있어야 디스크 데이터 복사 없이 빠르게 종료**된다. 본 시나리오는 다음 두 패턴 중 하나를 사용:

- 패턴 A: 113001의 디스크가 §4 VM-S3에서 `kcy0122-nfs-test-01`로 이동된 상태 → 공유 storage라 디스크 복사 없음 (빠름, 수십 초)
- 패턴 B: 113001 디스크가 `local-zfs`(nd03 로컬)에 있음 → `with-local-disks` 옵션으로 디스크도 함께 복사 (느림, 수 분)

본 가이드는 **패턴 A를 우선 권장**. §4 VM-S3을 먼저 진행했어야 함.

#### 사전 박제

```bash
# VM 위치 + storage 종속성
ssh pve-nd03 "qm config 113001 | grep -E '^(scsi|virtio|name)'"
# 기대: scsi0가 kcy0122-nfs-test-01:113001/...qcow2 (공유 storage)

# 마이그레이션 가능 여부 사전 점검
ssh pve-nd03 "qm migrate 113001 pve-nd04 --dry-run 2>&1 | head -20"
# 기대: "would migrate" 메시지 + 실제 변경 없음

# 게스트 IP·MAC 기록 (마이그레이션 후 동일해야)
ssh pve-nd03 "qm guest cmd 113001 network-get-interfaces 2>/dev/null | jq -r '.[] | \"\\(.name) \\(.\"hardware-address\") \\(.\"ip-addresses\"[0].\"ip-address\")\"' 2>/dev/null"
```

#### CMP UI 동작

1. CMP UI → 가상머신 → `113001` → 우상단 또는 더보기 → **마이그레이션** (UI-VM0100-04)
2. 입력
   - 대상 노드: `pve-nd04`
   - 마이그레이션 방식: 온라인 (Live) — 기본
   - **로컬 디스크와 함께(--with-local-disks)**: 패턴 A인 경우 체크 해제, 패턴 B인 경우 체크
3. **마이그레이션** 클릭

##### DevTools 캡처

- 기대 API: `POST /api2/json/nodes/pve-nd03/qemu/113001/migrate`
- 페이로드: `{ "target": "pve-nd04", "online": 1, "with-local-disks": 0 }`
- 응답: 200 + UPID 문자열 (작업 ID)
- 진행 상태 polling: `GET /api2/json/nodes/pve-nd03/tasks/{UPID}/status`, `.../log`

#### Layer 3-5 검증

```bash
# 마이그레이션 작업 진행 추적
upid="UPID:pve-nd03:..."   # DevTools 응답에서 복사
ssh pve-nd03 "tail -f /var/log/pve/tasks/active" &
# 또는: pvesh get /nodes/pve-nd03/tasks/$upid/log

# 작업 완료 확인
pvesh get /cluster/resources --output-format json | jq '.[] | select(.vmid==113001) | {node: .node, status: .status}'
# 기대: { "node": "pve-nd04", "status": "running" }

# qemu-server 파일은 호스팅 노드에만 존재
for n in pve-nd0{1..5}; do
  ssh "$n" "ls /etc/pve/qemu-server/113001.conf 2>/dev/null && echo \"존재: $n\""
done
# 기대: nd04에서만 파일 보고. (pmxcfs FUSE 동기로 5노드 모두에서 보일 수도 있음 — md5는 동일)

# nd03에 잔재 자원 확인 (이게 핵심 결함 검증)
ssh pve-nd03 "qm list | grep 113001 || echo 'OK: nd03에 113001 없음'"
ssh pve-nd03 "ps aux | grep -i 'qemu.*113001' | grep -v grep || echo 'OK: nd03에 qemu 프로세스 없음'"
ssh pve-nd03 "ls /var/run/qemu-server/113001* 2>/dev/null || echo 'OK: nd03에 런타임 파일 없음'"
```

#### Layer 6: 게스트 측 다운타임 측정

마이그레이션 시작 전 별도 터미널에서 게스트 ping 시작:

```bash
# 다른 노드에서 게스트로 ping (1초 간격)
ssh pve-nd05 "ping -i 1 -O 10.99.40.150" > /tmp/kcy0122-2026-04-27/migration-ping.txt
# 마이그레이션 진행 중에 ping 손실 카운트
# 기대: 라이브 마이그레이션은 1~3초 다운타임 (게스트 정지 시점)
```

마이그레이션 완료 후:

```bash
# ping 손실 분석
grep -c 'no answer' /tmp/kcy0122-2026-04-27/migration-ping.txt
# 또는 ping 결과 마지막 통계 캡처

# 게스트 측 — 마이그레이션 인지하지 못해야 정상
# 게스트 SSH:
uptime    # 부팅 시간 그대로
sudo dmesg | tail -5   # 마이그레이션 관련 메시지 없어야

# 게스트 IP·MAC 동일 확인
ip a show ens18 | grep -E 'ether|inet '
# 기대: 사전 박제와 동일 MAC + IP
```

#### 결함 후보

```bash

# 위험 = MOUNTPOINT 또는 FSTYPE에 값 (다른 자원 점유 중)

# PV(LVM)·ZFS 멤버 여부 추가 점검
```

### 6.3 ND-D3. 새 LVM 볼륨 그룹 생성 (L3×R2, 30분)

#### 위험성

빈 디스크에 새 PV(Physical Volume)+VG(Volume Group)를 만든다. CMP UI는 **선택한 디스크를 wipe하고 PV로 초기화**한다 — 사전 정찰에서 빈 디스크임을 확신해야 한다.

격자 L3(단일 노드 디스크 변경)·R2(VG 제거로 가역. 단 디스크 데이터는 비가역 wipe된 상태). **본인이 만들기 전에 다른 데이터가 없었음**을 §6.0에서 확인.

#### 사전

```bash
# §6.0 절차 다시 한번 — 타깃 디스크 식별
ssh pve-nd03 "lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,FSTYPE,FSUSE%"
# 빈 디스크 후보: /dev/sdX (TYPE=disk, MOUNTPOINT/FSTYPE 모두 비어있음)

# 추가 안전망 — 디스크 바이너리 첫 1MiB가 0인지
ssh pve-nd03 "dd if=/dev/sdX bs=1M count=1 status=none | hexdump -C | head"
# 기대: 거의 모두 00 또는 알아볼 수 있는 시그니처 없음
```

빈 디스크가 없으면 **본 시나리오 진행 불가**. 운영팀에 빈 디스크 1개 마운트 요청 후 진행.

## 8. Node Network 시나리오 (영역 E — 정찰 + 변경)

본 영역은 노드별 `/etc/network/interfaces` 변경이며 **pmxcfs 동기 안 됨**. ifupdown2가 변경을 적용할 때 **잠시 네트워크가 끊길 수 있다**(예: bridge MTU 변경). 변경은 **slave 없는 새 bridge 또는 sub-interface(VLAN) 한정**, 기존 vmbr0/1/2 직접 수정 금지.

### 8.0 모든 변경 시나리오 공통 진입 절차

```bash

# 2. ifreload 가능 여부 확인 (변경 적용 도구)
ssh pve-nd03 "which ifreload"
# 기대: /usr/sbin/ifreload (ifupdown2 패키지)

# 3. 작업 노드 SSH 세션 다중 확보 (네트워크 끊김 대비)
# 메인 SSH 세션 외에 별도 세션 1개를 미리 열어둠

# 4. PVE는 /etc/network/interfaces.new 임시 파일을 사용 — UI에서 "변경 사항 적용" 클릭 시 .new → 본 파일로 atomic 교체 + ifreload
```

### 8.6 NN-N5. VLAN sub-interface 추가 (L3×R2, 40분)

### 8.7 NN-N6. Linux Bond 추가 (slave 2개, IP 없음) (L4×R2, 50분)

#### 시나리오 의의

물리 NIC 2개를 묶어 단일 논리 인터페이스로 만든다. **슬레이브가 활성 NIC면 그 즉시 트래픽이 끊긴다** — 본 시나리오는 반드시 **빈 NIC 2개**(어떤 bridge·bond에도 멤버가 아닌 것)로 진행한다. 격자 L4(빈 NIC라도 노드 네트워크 데몬 영향) × R2(R1처럼 단순 텍스트 삭제로는 안 끝나며, ifreload 후 인터페이스 잔재 정리 필요).

bond mode 4종 중 본 시나리오는 **`active-backup`**을 사용한다. 외부 스위치 협조 없이도 동작하며 슬레이브 한 쪽 다운 시 다른 쪽으로 즉시 전환된다. LACP(`802.3ad`) 모드는 스위치 측 LACP 그룹 사전 구성이 필수이므로 본 가이드 한도(L4×R2)를 넘는다.

> 공식: [Proxmox VE Wiki — Network Configuration: Linux Bond](https://pve.proxmox.com/wiki/Network_Configuration#_linux_bond)

#### 사전

```bash
# 작업 노드 nd03의 빈 NIC 2개 식별 — bridge·bond 멤버 아닌 것
ssh pve-nd03 "
  echo '--- 전체 물리 NIC ---'
  ip -br link | awk '/^en|^eth/ {print \$1, \$2}'
  echo '--- bridge 멤버 ---'
  brctl show 2>/dev/null | awk '/^[a-z]/ {b=\$1; next} {print b, \$NF}' | grep -E 'en|eth'
  echo '--- /etc/network/interfaces 등록 NIC ---'
  awk '/^iface (en|eth)/ {print \$2}' /etc/network/interfaces
"
# 빈 NIC 후보: ip link에는 보이는데 brctl에 멤버 아니고
#              interfaces에 manual 외 정의 없는 것.

# /etc/network/interfaces 백업 (§8.0 절차)
ssh pve-nd03 "cp /etc/network/interfaces /etc/network/interfaces.kcy0122-baseline-$(date +%H%M%S)"

# 작업 직전 SSH 세션은 mgmt 평면(vmbr0/enp13s0)으로 들어와 있는지 재확인
ssh pve-nd03 "ip route get 1.1.1.1 | head -1"
# 기대: 출력에 'dev vmbr0' 또는 mgmt 평면 NIC 명시
```

> **진입 차단 조건**: 빈 NIC가 2개 미만이거나, 후보 NIC가 어떤 평면(mgmt/corosync/storage/VM)에 박혀 있다면 **본 시나리오는 보류**한다. 부록 E 운영팀 사전 협조 항목으로 빈 NIC 2개 확보를 요청한다. 우회 시도 금지.

본 가이드는 빈 NIC를 `enpXs0`, `enpYs0`로 표기한다. 실제 식별된 NIC명으로 치환하여 진행한다.

#### CMP UI 동작 (1단계 — staging)

### 8.8 NN-N7. OVS Bridge 추가 (slave 없음) (L3×R1, 30분)

```bash
# 사용 안 한 vmbr 번호 확보 — Linux Bridge 시나리오와 충돌 회피
```

### 8.9 NN-N8. OVS IntPort 추가 (NN-N7 위) (L3×R2, 40분)

### 8.10 NN-N9. OVS Bond 추가 (slave 2개, vmbr88 attach) (L4×R2, 60분)

#### 시나리오 의의

OVS 데이터 평면에서 동작하는 Bond. **§8.7 Linux Bond와 동일하게 빈 NIC 2개를 요구**하며, OVS Bridge에 attach되어 그 bridge의 외부 트래픽 입출구가 된다. 본 시나리오는 §8.8 vmbr88 기반에서 OVS Bond 구성 → vmbr88의 슬레이브로 등록 → 트래픽 검증을 한 사이클로 묶는다.

격자 L4(빈 NIC라도 OVS 데몬 영향 + bridge attach) × R2(R1로 안 끝남 — 본드 해체 + bridge attach 해제 + ifreload 후 잔재 정리 다단계).

bond mode: **`active-backup`** 채택. OVS의 `balance-tcp`/`balance-slb`는 외부 스위치 LACP/L2 학습 협조 필요로 본 가이드 한도 초과.

> 공식: [Proxmox VE Wiki — Open vSwitch: Bond](https://pve.proxmox.com/wiki/Open_vSwitch#Bond)

#### 사전

```bash
# §8.8 vmbr88 존재 확인 (부모 bridge)
ssh pve-nd03 "ovs-vsctl br-exists vmbr88 && echo OK"

# §8.7 Linux Bond와 슬레이브 NIC 충돌 회피 — Linux Bond bond0이 살아있으면
# 거기 박힌 NIC는 OVS Bond 슬레이브로 못 씀
ssh pve-nd03 "cat /proc/net/bonding/bond0 2>/dev/null | grep 'Slave Interface'"
# Linux Bond가 살아 있으면 그 슬레이브 NIC 회피.

# OVS Bond에 쓸 빈 NIC 2개 재식별 (§8.7과 다른 NIC여야 함)
ssh pve-nd03 "ip -br link | awk '/^en|^eth/ {print \$1, \$2, \$3}'"
# 후보 NIC: master 표기 없고, brctl·bond에 멤버 아닌 NIC 2개
# 본 가이드는 enpAs0, enpBs0로 표기. 실제 NIC명으로 치환.
```

#### 결함 후보

- 슬레이브 NIC가 §8.7 Linux Bond `bond0`의 슬레이브로 이미 박혀있는데도 만들기 통과 → **이중 본드 데이터 평면 충돌 (P0)**
- `ovs_bridge` 누락 → 본드는 등록되지만 어떤 bridge에도 attach 안 됨 → 트래픽 흐를 곳 없음
- mode가 `bond_mode` 별도 필드로 전송되어 `ovs_options` 누락 → OVS는 default mode(active-backup이 아닌 SLB일 수 있음)로 동작
- vmbr88 제거 시 ovsbond0 자동 정리 안 됨 → 고아 OVS 자원 (P0)
- LACP 옵션을 UI가 노출하지만 active-backup mode에서도 LACP 활성화 가능하게 됨 → mode 의존 관계 검증 부재

#### 되돌리기 (R2)

**반드시 의존 역순**: ovsbond0(§8.10) → vlan200(§8.9) → vmbr88(§8.8). 각 단계 사이 변경 사항 적용 누락 시 잔재 누적된다.

```text

[2] vmbr88의 ovs_ports에서 ovsbond0이 빠졌는지 확인
[3] 슬레이브 NIC가 ovs-system에서 풀려 standalone으로 돌아왔는지 확인
```

## 10. 문제 발생 시

### 10.1 즉시 중단 신호 (핸드북 09 §5)

다음 중 하나라도 보이면 **테스트 즉시 중단** + Slack `#cmp-test` 채널 STOP 메시지:

- `pvecm status` 결과 Quorate=No 또는 votes < 5
- 5노드 동시 SSH에서 일부 응답 없음
- TrueNAS(nd06 또는 nd07) 응답 없음
- 30분 동안 ERROR 로그 10만 건 초과 (특정 노드)
- `dmesg`에서 OOM Killer 활성화 또는 Call Trace
- 다른 테스터 또는 admin01의 작업 알림

### 10.2 자주 만나는 문제

#### Q. CMP UI 작업 후 PVE 실상 변경 없음
- DevTools에서 응답 status 확인 — 200이면 PVE까지 갔어야
- 응답이 4xx/5xx면 CMP가 호출은 했으나 PVE가 거부 — Layer 3 `pvesh`로 같은 동작 직접 시도하여 PVE 측 에러 파악
- 200인데 PVE 변경 없으면 **CMP 캐시 결함** — 김찬영의 4/22 백업 결함 보고와 동일 패턴

#### Q. PVE에는 변경 있는데 CMP UI에 표시 안 됨
- CMP UI 새로고침 후 재확인
- 그래도 안 보이면 **CMP 동기 결함** (스테이징 워크플로우 §4.2)
- 5노드 다른 곳에서 PVE WebUI 직접 접속 — PVE는 보이는가

#### Q. 5노드 md5 불일치
- pmxcfs 동기 결함 — 즉시 §9.1 중단 신호
- 한 노드만 다른 md5면 그 노드의 pmxcfs 상태 점검:
  ```bash
  ssh {문제노드} "systemctl status pve-cluster"
  ssh {문제노드} "pmxcfs -V"
  ```

#### Q. 게스트 인터페이스/디스크 인식 못 함
- VM 재부팅 (model 변경 등은 hotplug 안 됨)
- guest-agent 설치 여부 확인: `qm guest cmd 113001 ping`
- guest-agent 미설치 시 일부 hotplug 미작동 — 결함 아닌 환경 문제

#### Q. NFS 마운트 안 됨
- TrueNAS export 권한 (Maproot User=root) — 4/22 결함의 원인
- storage 평면 IP에서 ping 가능한가: `ssh pve-nd03 "ping -c 3 10.99.30.17"`
- showmount: `ssh pve-nd03 "showmount -e 10.99.30.17"` — export 목록 보이는가

#### Q. iSCSI LUN이 보이지 않음 (§7.3·§7.4)
- target discovery: `ssh pve-nd03 "iscsiadm -m discovery -t st -p 10.99.30.17"`
- session 활성: `ssh pve-nd03 "iscsiadm -m session"`
- session은 있는데 LUN 미발견: TrueNAS 측 initiator group 권한 확인
- multipath 인지: `ssh pve-nd03 "multipath -ll 2>/dev/null"` — 같은 LUN이 sda/sdb 둘로 보이면 multipath 적용

#### Q. Node Network 변경 사항 적용 후 SSH 끊김
- 다른 SSH 세션 또는 PVE Web UI 콘솔에서 진단
- 핸드북 09 §5 L3 신호 (즉시 보고)
- 운영팀에 IPMI/iDRAC 통한 콘솔 복구 요청
- 본 가이드 §8.0의 "SSH 세션 다중 확보" 권고를 지켰다면 이 상황 회피 가능

#### Q. ifreload 실패
- `ssh pve-nd03 "ifreload -a -d 2>&1 | tail -50"` — 디버그 출력
- /etc/network/interfaces.new 문법 오류 가능성 — `ifup --print-dependency-graph` 또는 `pvesh get /nodes/pve-nd03/network`로 검증
- baseline 파일로 즉시 복원: `cp /etc/network/interfaces.kcy0122-baseline-* /etc/network/interfaces && ifreload -a`

#### Q. LVM cluster shared 등록 후 nd04에서 VG 안 보임 (§7.4)
- nd04에 iSCSI 세션 별도 등록 필요할 수 있음 (storage.cfg에 nodes 제약이 nd03,nd04 둘 다 들어가야)
- `ssh pve-nd04 "iscsiadm -m discovery -t st -p 10.99.30.17"` 후 재시도
- pvesh `pvesh get /nodes/pve-nd04/storage/{id}/status`로 nd04 측 상태 확인

#### Q. 마이그레이션 후 nd03에 잔재 (§5)
- 핸드북 06 §2.8 VM 802 패턴
- `ssh pve-nd03 "ls /var/run/qemu-server/113001*"` — 런타임 파일 잔재
- `ssh pve-nd03 "ps aux | grep qemu | grep 113001"` — 프로세스 잔재
- 잔재 발견 시 즉시 결함 보고 (단독 정리 시도 금지 — admin01 동의 필요)
