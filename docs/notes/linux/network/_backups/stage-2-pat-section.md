## PAT ─ 하나의 공인 IP를 포트로 나눠 쓰기

앞 절의 SNAT/MASQUERADE에는 *말하지 않은 비밀*이 하나 있다. 내부망의 VM이 *여러 대*일 때 ─ 가령 VM-A, VM-B가 동시에 외부로 나간다면 ─ **이들의 출발지 IP는 모두 *같은* 공인 IP 하나로 바뀐다.** 그러면 외부에서 보기엔 둘 다 *같은 곳*에서 온 패킷이다.

여기서 의문이 생긴다. **응답이 그 공인 IP로 돌아올 때, 그걸 *어느 VM*에게 돌려줘야 하지?** 출발지 IP가 다 같아져 버렸는데?

답은 **출발지 포트(source port)**다.

### 다이어그램 ─ IP는 합치고, 포트로 가른다

```markdown
   내부 (사설)                  SNAT / PAT 변환              목적지
 ┌──────────────────┐
 │ VM-A 10.10.3.101 │
 │      :51000   ───┼──→   203.0.113.5 :51000  ───────→  8.8.8.8:443
 └──────────────────┘
                              ↑ IP는 하나로 통일
                              ↓ 포트는 다르게 재매핑
 ┌──────────────────┐
 │ VM-B 10.10.3.102 │
 │      :51000   ───┼──→   203.0.113.5 :52000  ───────→  8.8.8.8:443
 └──────────────────┘
      ↑ 둘 다 우연히                  ↑ 충돌을 피해
        같은 :51000을 썼다             포트를 갈아끼운다
```

VM-A와 VM-B가 *우연히 같은 출발지 포트(`51000`)*를 썼더라도, NAT은 *공인 IP 쪽 포트를 서로 다르게*(`51000`, `52000`) 재매핑한다. 그래서 외부에서 보면 — **같은 IP, 다른 포트**의 두 연결로 깔끔히 구분된다.

### conntrack이 기억하는 매핑

이 변환을 *기억*하는 게 conntrack(또는 pf의 state table)이다.

| 원래 (사설)         | 변환 후 (공인)      | 목적지        |
| ------------------- | ------------------- | ------------- |
| `10.10.3.101:51000` | `203.0.113.5:51000` | `8.8.8.8:443` |
| `10.10.3.102:51000` | `203.0.113.5:52000` | `8.8.8.8:443` |

응답이 돌아오면, *역방향*으로 이 표를 조회해 제 주인을 찾는다.

```markdown
8.8.8.8:443 → 203.0.113.5:51000   ⟹ 조회 ⟹   10.10.3.101:51000  (VM-A)
8.8.8.8:443 → 203.0.113.5:52000   ⟹ 조회 ⟹   10.10.3.102:51000  (VM-B)
```

### 핵심 ─ 포트가 *식별 꼬리표*가 된다

> **출발지 IP는 하나로 합쳐지지만, 출발지 포트가 각 연결(=각 VM)을 구분하는 꼬리표 역할을 한다.**

Stage 2 앞에서 본 conntrack의 **5-tuple**(protocol, src IP, src port, dst IP, dst port)을 떠올리자. PAT에서 *src port*가 바로 이 구분의 핵심 축이다. IP를 하나로 합쳐 *공인 IP를 절약*하면서도, 포트로 *수만 개의 연결을 동시에 구분*할 수 있다 (포트는 16비트 = 65,536개).

이 기법을 **PAT(Port Address Translation)** 또는 **NAPT(Network Address Port Translation)**라 부른다. 리눅스의 **MASQUERADE**가 하는 일이 정확히 이것이고, 가정용 공유기가 *공인 IP 하나로 집 안의 수십 대 기기를 동시에* 인터넷에 내보내는 원리도 같다.

> **변곡점** — *"출발지 IP가 다 같아지면 응답은 어떻게 제 주인을 찾지?"*라는 의문이 풀리는 순간, NAT이 *단순한 IP 치환*이 아니라 **IP + 포트의 정교한 매핑 시스템**임이 보인다. 그리고 *왜 conntrack(상태 기억)이 NAT의 필수 짝인지*도 분명해진다 ─ 이 매핑표가 없으면 응답은 길을 잃는다.
